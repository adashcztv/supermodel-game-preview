## Findings (source fixes belong to the game source, not this preview repo)

**F1 — Space re-opens a panel instead of advancing dialogue (keyboard, medium).**
After a toolbar panel (Save/Load/Log/Settings) is closed with Escape or ×, focus
returns to its toolbar button (`#quick-save` etc.). The next Space press — which
the in-game help documents as "press Space to finish a line" — activates the
focused button and re-opens the panel. Same after a mouse click on Skip/Auto: the
toolbar button keeps focus. Repro: open Save → Escape → Space → Save opens again.
Suggestion: handle Space/Enter for advancing at document level while focus is in
the quick-bar (and preventDefault), or move focus back to `#next-button` when a
panel closed by pointer, keeping Escape focus restore for keyboard users.
Root cause in `assets/story-Dl52z295.js` (global `keydown` listener next to
`window.smPreview`): advancing runs only when
`!e.target.closest('button') || key==='r' || digit-in-#choices`; any other
focused button gets the browser's native Space/Enter activation. The native
`<dialog>.close()` restores focus to the opener (`#quick-save`, …), so the
toolbar button is the target of the next Space.

**F2 — Scene container can be scrolled by 30–50 px (layout robustness, low).**
*Update after re-test:* not triggered by normal pointer play. A full re-run with
coordinate-only mouse clicks (title → intro → 25 lines → choice) kept
`scene.scrollTop/Left = 0`. The shift is triggered by `Element.scrollIntoView()`
with `block:'center'` (used by the in-app browser automation for ref clicks;
some assistive technology and find-in-page do the same):
`#quick-load.scrollIntoView({block:'center'})` → `scene.scrollTop = 50`;
`scrollIntoView({block:'nearest'})` and `focus()` → 0.
Cause: `section.scene` is `overflow: hidden` (still a programmatic scroll
container) while `.character-wrap` overflows it — desktop rule
`.character-wrap{…bottom:-50px…}` (bottom 818 px in a 768 px viewport), mobile
rule `.character-wrap{width:116vw…}` (−30…405 px in 375 px). Once shifted, it
stays shifted (top bar cut / dark band) until the next full render.
Verified fix: injecting `.scene{overflow:clip}` → the same `scrollIntoView`
leaves the scene at 0/0. Same pattern exists on `#title-screen` (scrolled
15/20 px by a `scrollIntoView` on `#title-new`).

**F3 — Combat fails to start if the page is not rendering for 15 s (medium).**
`combat-BcZ9nSUS.js`: after `createUnityInstance` resolves, a wall-clock
`setTimeout(…, 15e3)` rejects with "Unity loaded, but the 3D scene did not
start." unless the scene-ready flag is set. Unity sets it only from rendered
frames, and a hidden/minimised/background page has no `requestAnimationFrame`
(measured: 0 rAF in 2 s while the pane was hidden). Reproduced 2/2 with the page
not being rendered: "Opening the archive · 100%" → "The archive could not start".
The same page started fine while visible. Real-player case: tapping "Enter the
archive" and switching tab/app while the ~61 MB native build loads.
Recovery exists (Reload the archive / Return to the story) but it costs a full
reload. Suggestion: count the watchdog only while
`document.visibilityState==='visible'` and frames arrive (pause on
`visibilitychange`), and/or let a late scene-ready dismiss the error.

**Fix (source, not released):** `eleventake/supermodel-game` branch
`claude/windows-f1-f2-f3-20261016`, commit `43a1f75` on top of Codex's
`codex/windows-source-20261016` (`98e83a3`). Before/after with Playwright 1.63
headless Chromium (GPU), same scripts against this preview (before) and the
source dev server 127.0.0.1:4296 (after):
- F1 Save/Load/Settings by pointer → Escape → Space: before re-opened 3/3,
  after advanced 3/3 with focus on `#next-button`; Skip/Menu/House by pointer
  likewise; keyboard Enter → Escape still returns focus to `#quick-save`.
- F2 `scrollIntoView({block:'center'})`: before 50/50/30 px shift
  (1280x800, 1024x768, 375x812), after 0 on all three.
- F3 page hidden (no rAF) for 25 s after "Enter the archive": before
  "could not start" and no recovery after showing; after no error, combat
  started after the page was shown again.
- Also: `game/public/** -text`, because Windows `core.autocrlf` rewrote 30
  byte-hashed runtime files and `verify-release` failed; now it passes.

**Observations (low, verify in source):**

- After returning to a bookmark from `/?combat=1&resume=1` the URL keeps the stale

(headless SwiftShader made each combat round ~45 s, so GPU was used):

  ending `sm-end-open_protocol` (~9 min per run), 20 combats won

  ending `friends-end-contested_archive`, 16 combats won, wrong deductions are
  explained and the story continues (retry path works), 142 unique nodes.

  errors were transient connection refusals of the local test server.

  replaces "Your turn" at low health); a game behaviour, not a bug.

  after hub choices. Hubs have a scrollable `#choices` list; scrolling a
  partly hidden choice into view also scrolls `.scene`.

  fourth (channel) was mid-fight when the 12 min test budget ended; 141 unique
  nodes, no errors, 11 F2 shifts.

  Chromium 12 min: one complete run to `sm-end-open_protocol` and into the
  next, 5 combats won, 154 unique nodes, **0 shifts**, no errors.
